# 返信とまとめのコメントの書き方、計画のファイル

`dev-relay pr respond` が検査する形。計画と本文は、`dev-relay pr feedback` の `fb.drafts` のフォルダに置く。

## 返信（スレッドごと）

- 相手の指摘への答えだけを書く。1〜3文。あいさつや前置きは付けない。
- 言語は、手順8のとおり `dev-relay pr recent` で決めた言語に合わせる。
- 直したときは、何をどう直したかと、`{{commit}}` を書く。コマンドが、投稿の直前に40文字の SHA に置き換える。
- 直さないときは、理由を書く。「再現しなかった」なら、実行したコマンドと結果を1行で。「意図した選択」なら、その理由を。
- 本文に `{{commit}}` を書けるのは、計画に `commit` か `commit-ref` があるときだけ。無いのに書くと `commit-placeholder` で止まる。
- **印（`<!-- dev-relay:` で始まるもの）は、コマンドが末尾に付ける。本文には書かない。** 書くと `reserved-marker` で止まる。
- 手元のパス、秘密の値、顧客の名前を入れない。ファイルは、リポジトリのルートからの相対で書く。
- スレッドの解決はしない。返信すると、そのスレッドは相手の返事待ちになる。

### 例: 直したとき

作り物の内容。`mean` が空のリストで例外になる、という指摘。

````markdown
空のリストのときは 0.0 を返すようにしました（`{{commit}}`）。`test_mean_empty` を足してあります。
````

### 例: 直さないとき

作り物の内容。`mean` を `statistics.mean` に置き換えてはどうか、という提案。

````markdown
置き換えません。この関数は整数の列を `float` で返す前提で、呼び出し側がその型に依存しています。`statistics.mean` は入力によって `int` や `Fraction` を返すので、戻り値の型が変わります。
````

## まとめのコメント（レビューの本文と会話のコメント）

- 会話のコメントにはスレッドが無いので、答えをまとめて1つのコメントにする。何に答えたかが分かるように、相手のコメントを短く引用する。
- 答えたものの id を、計画の `comment` の行に並べる。印（`<!-- dev-relay:handled ... -->`）は、コマンドが並べた id の版を付けて末尾に足す。本文には書かない。
- 答えるものが無いもの（「LGTM」だけなど）も、対応済みにするなら id を並べてよい。
- 対応済みにしたものは、あとで本文が編集されると、また todo に出る。

### 例

作り物の内容。レビューの本文1つと、会話のコメント1つに答える。

````markdown
> 全体の方針は良いが、命名を揃えてほしい

`calc_*` に揃えました（`{{commit}}`）。

> README の使い方も更新してほしい

この PR では触れません。別の PR で、使い方の節をまとめて直します。
````

## 計画のファイル

1行に1つの動作。`#` で始まる行と空の行は読み飛ばす。区切りは空白1つ以上。

```
commit <メッセージのファイル名>
commit-ref <SHA>
reply <スレッドの id> <本文のファイル名>
comment <本文のファイル名> <対応済みにする id> [<id>...]
rerun <run の id>
```

| 動作 | 意味 |
|---|---|
| `commit` | ステージ済みの変更（index）を、このメッセージで1つのコミットにする。コミットするのは `--confirm` のとき。ステージされていない変更と、追跡していないファイルは入らない |
| `commit-ref` | すでにあるコミット（40文字の SHA）を、`{{commit}}` に使う。一部が失敗したあとのやり直しで使う |
| `reply` | スレッドに返信する。スレッドの id は一覧の `###` の見出し（`PRRT_` で始まる） |
| `comment` | まとめのコメントを会話に投稿する。並べる id は、一覧の `###` の見出し（`PRR_` か `IC_` で始まる）。版は書かない |
| `rerun` | 失敗した CI の run のうち、失敗したジョブだけをやり直す |

- `commit` と `commit-ref` は、合わせて1つまで。`comment` は1つまで。同じスレッドへの `reply` と、同じ run の `rerun` は、それぞれ1つまで。
- 本文とメッセージのファイル名は、計画と同じフォルダにあるファイルの名前（英数字と `.` `_` `-` だけ。`/` を含めない）。
- push は計画に書かない。`commit` があるか、`pr.head-state=ahead` なら、`pr respond` が先頭を push する。

### 例

作り物の id。スレッド2つに返信し、レビューの本文とコメントにまとめて答え、直した変更を1つのコミットにする。

```
# 直した指摘
commit msg.txt
reply PRRT_aaaa r1.md
# 直さない指摘
reply PRRT_bbbb r2.md
# レビューの本文と会話のコメント
comment c1.md PRR_cccc IC_dddd
```

## `respond.reason` の意味

`pr respond --dry-run` が、`respond.reason=<理由>;<理由>...` で出す。

| 理由 | 直し方 |
|---|---|
| `bad-line:<行番号>` | その行の動作、引数の数、id、ファイル名の形を直す |
| `duplicate:<行番号>` | 同じスレッドへの2つ目の `reply`、2つ目の `comment`、同じ run の2つ目の `rerun`、2つ目の `commit` / `commit-ref` を消す |
| `nothing-staged` | `commit` があるのにステージ済みの変更が無い。ステージするか、`commit` の行を消す |
| `index-unmerged` | 競合の解消されていないファイルがある。解消してからステージする |
| `operation-in-progress` | マージ、cherry-pick、revert の途中（`MERGE_HEAD` などがある）。その操作を `git commit` で終えるか取りやめてから、もう一度検査する |
| `staged-without-commit` | ステージ済みの変更があるのに `commit` が無い。`commit` の行を足すか、`git restore --staged <パス>` で外す |
| `commit-ref-not-in-head:<SHA>` | `commit-ref` の SHA が、手元の HEAD の祖先でない。SHA を確かめる |
| `commit-placeholder:<ファイル名>` | 本文に `{{commit}}` があるが、`commit` も `commit-ref` も無い。どちらかを足すか、本文から消す |
| `not-todo:<id>` | `reply` のスレッドや `comment` の id が、todo でない（返事待ち、解決済み、無い id）。`pr feedback` をやり直して id を確かめる |
| `not-failed:<run の id>` | `rerun` の run が、この PR の CI の fail の行に無い |
| `missing-file:<ファイル名>` | 本文かメッセージのファイルが無い、読めない |
| `empty-body:<ファイル名>` | 本文かメッセージが空白だけ |
| `too-long:<ファイル名>` | `{{commit}}` を置き換え、印を足したあとが 60000 バイトを超える。短くする |
| `rerun-with-push:<run の id>` | push する計画に `rerun` がある。`rerun` の行を消す（push すると新しい先頭の CI が動く） |
| `reserved-marker:<ファイル名>` | 本文に `<!-- dev-relay:` がある。消す |
| `leak:<種類>@<ファイル名>:<行番号>` | 手元のパスや秘密の形が入っている。その行の値を消すか、別の語に置き換える |
| `nothing-to-do` | 計画に動作が無く、push もしない |
