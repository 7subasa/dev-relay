# レビュアーの選ばれ方

レビューを誰に頼むかは、スクリプトが毎回その場で決める。メインセッションが選ぶ必要は無いが、何が選ばれるか、なぜ飛ばされたか、いつ追加のレビュアーを使うかは知っておく。

## 1. 選ばれ方

役割ごとの候補の一覧が、プラグインの `config/roles/` にある（`design-review.conf`、`code-review.conf`、`code-review-extra.conf`）。上にある候補ほど優先する。スクリプトは候補を上から順に見て、使えない理由が1つも無い最初の候補を選ぶ。

役割の候補は、手元で上書きできる（`dev-relay config role`）。上書きがあれば、プラグインの一覧の代わりにそちらを読む。今どちらを読んでいるかは、`dev-relay doctor` の `role.<役割>.source`（`default` / `override`）で分かる。上書きのときは `role.<役割>.override`（`current` / `stale`）も出る。`stale` は、上書きを作ったあとに、プラグインの既定の一覧が変わったという意味。

上書きを書くときに守ること。

- 同じ id は、どの役割でも同じ定義を指す。別の役割で違う定義に同じ id を使うと、エラーになる。追加のレビュアーの除外や `--reviewer` が、id だけで候補を見分けているため。
- backend が `claude` の候補は、model と effort を `-` にする。Claude のレビュアーは決まったエージェントで動き、model を渡す経路が無い。
- `vendors` には、実際の送り先を書く。backend や model から分かる提供元が `vendors` に無い行は、エラーになる。

使えない理由は、次のとおり。

| 理由 | 意味 |
|---|---|
| `codex-not-installed` / `codex-not-logged-in` | Codex CLI が入っていない、ログインしていない |
| `cursor-not-installed` / `cursor-not-logged-in` | Cursor CLI が入っていない、ログインしていない |
| `jq-not-installed` | Cursor のレビュアーには `jq` が要る |
| `not-a-git-repo` | Cursor のレビュアーは、作業ツリーの検査のために git リポジトリが要る |
| `metered-off` | 利用量に応じて課金されうる候補で、設定の `metered` が `auto` でない |
| `vendor-not-allowed:<名前>` | 候補の送り先のうち、許可されていないものがある |
| `same-as-primary` | 通常のレビューで使うレビュアーと同じ（追加のレビュアーでだけ起きる） |

Claude のレビュアー（backend が `claude`）には、道具に関する理由が付かない。そのため、どの環境でも最後には Claude が選ばれ、レビューは必ず進む。

道具が入っているかどうかで、選ばれるものは次のように変わる（送り先がすべて許可されている場合。許可が無ければ、どの環境でも Claude になる）。

| 環境 | 設計・コードレビュー | 追加のレビュアー |
|---|---|---|
| Codex あり、Cursor あり | Codex | `metered` が `auto` なら Cursor 経由の別モデル、`off` なら Claude |
| Codex あり、Cursor なし | Codex | Claude |
| Codex なし、Cursor あり | Cursor 経由のモデル | `metered` が `auto` なら Cursor 経由の別モデル、`off` なら Claude |
| どちらもなし | Claude | なし |

今どれが選ばれるか、なぜ飛ばされたかは、`dev-relay doctor` の `role.*` と `role.*.skipped` で分かる。1回だけ別の候補を使うときは、`dev-relay review ... --reviewer <id>` を使う。ただし、`--reviewer` でも `metered` と送り先の許可の条件は越えられない。使えない候補を指定したときは、理由が出て終了コード 1 になる。

## 2. 送り先の許可

差分と設計書は、選ばれたレビュアーの提供元に送られる。コードを送ってよい提供元は、2か所で決まる。

| 層 | 場所 | 値 |
|---|---|---|
| リポジトリごとの設定 | そのリポジトリの git のローカル設定 `dev-relay.vendors` | 提供元の一覧 / `none` |
| 利用者の既定 | 設定フォルダの `vendors` | 提供元の一覧 / `none` / `ask` |

- リポジトリごとの設定があれば、それを使う。無ければ利用者の既定を使う。
- 一覧は `openai,cursor,google` のようにカンマで区切る。`none` は外部には送らない。`ask` は、リポジトリごとに尋ねる。
- 設定がどちらにも無ければ、外部には送らない。選ばれるのは Claude のレビュアーだけになる。
- `anthropic` は、一覧に無くても常に許可として扱う。メインセッションが Claude で、コードはすでに送られているため。
- 候補を使えるのは、その候補の送り先がすべて許可されているとき。

今の値と出どころ（`repo` / `user` / `ask` / `unset`）は、`dev-relay config vendors` で見られる。変えるのは `/dev-relay:setup` か、`dev-relay config vendors --user <一覧|none|ask>`（利用者の既定）、`dev-relay config vendors --repo <一覧|none>`（このリポジトリ）。`--repo --reset` でリポジトリごとの設定を消せる。

### 尋ねるタイミング

`dev` スキルは、最初にやること 3 で `dev-relay doctor` を実行したあと、次の2つの場合だけ送り先を尋ねる。どちらも、`vendor-not-allowed` だけが理由で飛ばされた候補があるときに限る（道具が入っていないなら、尋ねても選べるものが無い）。

- `repo.vendors.source=unset`: `setup` がまだ。`/dev-relay:setup` の手順4（利用者の既定を選ぶ）をその場で行う。
- `repo.vendors.source=ask` で `git.repo=yes`: このリポジトリで使ってよい送り先を1度尋ね、答えを `dev-relay config vendors --repo <一覧|none>` で書く。断られたときも `none` を書くので、同じリポジトリで2度は尋ねない。

`claude -p` のように尋ねられない場面や、git リポジトリの外で `ask` のとき（答えを保存する場所が無い）は、尋ねずに、送り先が空のものとして進める。Claude のレビュアーが選ばれる。

## 3. 追加のレビュアーを使う基準

メインセッションが次のどれかに当たると判断したら、通常のレビュアーに加えて、`--extra` を付けた2本目を同時に動かす。ユーザーが追加のレビュアーを求めたときも使う。

1. 認証・認可、機密情報の扱いに触れる変更
2. データの移行・削除、スキーマ変更
3. 課金や金額の計算
4. 並行処理、再試行、冪等性に関わる変更
5. 公開 API や、複数のモジュールから呼ばれる共通部分の変更
6. 差分が大きい（目安: 変更ファイル10以上、または500行以上）
7. 設計レビューが「根本的に見直すべき」と返した設計

どれにも当たらなければ1本にする。レビュアーを増やすと採否の手間も増えるため。

起動の例は `runtime.md` の2節。追加のレビュアーは、通常のレビューで実際に使う id を除外して選ばれる（同じレビュアーを2回動かさないため）。

## 4. 追加のレビュアーを使ったときに守ること

- 使ったレビュアーと、追加した理由を報告に書く（`triage.md` の報告の形式）。
- 結果ファイルの末尾にトークン数があれば、報告に書く。
- `dev-relay review code --extra` が終了コード 4 を返したら、使える追加のレビュアーが無いという意味。追加なしで進め、そのことを報告に書く。飛ばされた理由は `dev-relay doctor` で見られる。

## 5. 利用量に応じて課金されうるレビュアー

候補の `billing` が `metered` のものは、利用量に応じて課金されうる。設定の `metered` が `auto` のときだけ選ばれる。既定は `off`。`auto` は、メインセッションが必要と判断したら使ってよいという意味。

変えるのは `/dev-relay:setup` か、`dev-relay config metered <off|auto>`。今の値は `dev-relay config metered` で見られる。

## 6. 読み取り専用の強さの違い

レビュアーは、作業ツリーを変えてはならない。ただし、守らせる仕組みはレビュアーで違う。

| レビュアー | 仕組み |
|---|---|
| Codex | OS の仕組み（サンドボックス）で書き込みを禁止する |
| Cursor | `--mode ask` で動かす。書き込みを OS の仕組みで禁止しているかは確かめられていないので、実行の前後で作業ツリーを比べ、変わっていたら終了コード 5 にする |
| Claude | 書く道具もコマンドを実行する道具も持たせない（`dev-relay:reviewer`） |

Cursor のレビューについて、守ること。

- Cursor のレビューが動いている間、メインセッションは作業ツリーに書き込まない。テストの実行と、差分を読むことに留める。
- テストが、無視されないファイルを作るリポジトリでは、終了コード 5 が誤って出ることがある。結果ファイルの一覧を見て、自分のテストが作ったファイルか、レビュアーが書いたものかを確かめる。スクリプトは元に戻さない。
- 検査の限界: 無視されているファイル（`.gitignore` の対象）と、`.git/` の中は見ない。submodule の中の変更は、親リポジトリから見た状態が変わるときだけ検出する。

詳細は `cursor-cli.md`。

## 7. Claude で代替するとき

選ばれたレビュアーが Claude のとき、スクリプトはレビューを実行せず、依頼文のファイルを書いて終了コード 3 で戻る。メインセッションが、Agent ツールを `subagent_type: "dev-relay:reviewer"` で呼ぶ。手順は `runtime.md` の「終了コード 3 が返ったとき」。

- 実装者と同じモデルにしない。実装に `dev-relay:implementer-hard` を使ったときは、Agent ツールの `model` に `sonnet` を指定して呼ぶ。`dev-relay:implementer` を使ったときは、指定しない（`dev-relay:reviewer` の既定のモデルが、実装者と別になる）。
- 同じ提供元のモデルで代替しているので、独立性は落ちる。報告の「レビュアー」欄に、代替したことを必ず書く。
- 自分の結論や見立ては、依頼文以外には渡さない。
