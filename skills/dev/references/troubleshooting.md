# うまくいかないとき

## Codex

| 症状 | 原因と対処 |
|---|---|
| `codex: command not found` | 未インストール。`npm i -g @openai/codex` を案内する。インストールとログインはユーザーの環境を変える操作で、対話も要るので、このスキルからは行わない |
| 認証エラー / 401 | 未ログインか、ログインが切れている。`codex login` を案内する。CI など対話できない環境では `CODEX_API_KEY` 環境変数を使う |
| `not inside a trusted directory` | Codex の信頼ディレクトリ設定で拒否されている。ユーザーに `codex` を一度対話で起動してもらい、そのディレクトリを信頼済みにしてもらう |
| `unexpected argument '--no-daemon'` | スクリプトは `codex --help` に載っているときだけ付けるので通常は出ない。出た場合は `codex --version` を確かめる |
| 出力が空、または途中で切れる | タイムアウト（既定15分、`DEV_RELAY_TIMEOUT` 秒で変更。終了コード 124）か、差分が大きすぎる。対象を `--base` から `--commit` に絞るか、設計書を分ける |
| `--base` でエラー | ブランチ名の誤り、またはそのブランチがローカルに無い。`git fetch` してから再実行する |
| 使用量の上限に達した | `--reviewer` で別の候補を指定する（`dev-relay doctor` の `role.*.skipped` で、どれが使えるかを確かめる）。Claude に代替したときは、代替したことを報告に書く |

## `dev-relay review` の終了コードと、飛ばされた候補

| 症状 | 原因と対処 |
|---|---|
| 終了コード 3 | 失敗ではない。選ばれたレビュアーが `claude` で、スクリプトは実行せず、依頼文のファイルを書いて戻った。Agent ツールで起動する（`runtime.md` の「終了コード 3 が返ったとき」） |
| 終了コード 4 | 使える追加のレビュアーが無い（`--extra`）。飛ばされた理由を `dev-relay doctor` の `role.code-review-extra.skipped` で見る。追加なしで進め、そのことを報告に書く |
| 終了コード 5 | レビューの前後で作業ツリーが変わった（Cursor のレビュー）。結果ファイルの `作業ツリーの変化を検出` の一覧を見て、自分のテストが作ったファイルか、レビュアーが書いたものかを確かめる。自動では戻さない |
| `cursor-not-logged-in` | `dev-relay doctor` の `skipped` に出る。`cursor-agent login` を案内する（自動化では `CURSOR_API_KEY`）。ログイン済みなのに出るときは、`cursor-agent status` の出力に `Logged in` が含まれるかを確かめる（`cursor-cli.md`） |
| `vendor-not-allowed:<名前>` | 候補の送り先が、許可されていない。意図どおりなら何もしない（許可された候補か、Claude で進む）。使いたいときは、`/dev-relay:setup` か `dev-relay config vendors --repo <一覧>`（このリポジトリ）、`dev-relay config vendors --user <一覧>`（利用者の既定）で許可する。今の値と出どころは `dev-relay config vendors` で見られる |

## 役割の上書き

| 症状 | 原因と対処 |
|---|---|
| エラーにファイル名と行番号が出て、レビューや `doctor` が止まる | 上書きのファイル（設定フォルダの `roles/<役割>.conf`）の、その行が壊れている。列の数や値の誤りのほか、backend と `vendors` の食い違い（例: backend が `codex` なのに `vendors` に `openai` が無い）でも出る。ファイルのその行を直す。直せないときは `dev-relay config role <役割> --reset` で、プラグインの既定の一覧に戻す |
| `dev-relay config role <役割> --from <ファイル>` が失敗する | 渡したファイルが同じ検査で落ちている。エラーのファイル名と行番号を見て、ファイルを直してから、もう一度実行する。失敗したときは、上書きは作られない |

## レビューの質

| 症状 | 原因と対処 |
|---|---|
| 指摘が的外ればかり | 設計書の「背景と制約」に、制約や「捨てた代替案とその理由」が書かれていないことが多い。書き足して再実行する。review モードでは `--intent` の目的が曖昧なことが多い |
| 指摘がほとんど再現しない | 目的の書き方が広すぎて、目的に反するかどうかを判定できていない。目的を「何が、どういう入力で、どうなればよいか」まで具体的にする |
| スタイルの指摘が多い | `--focus` で観点を足していないか確かめる。観点に「読みやすさ」などを入れると、プロンプトの「書かないもの」と衝突する |
| 「指摘なし」が返った | 有効な結果。件数を出させるために再実行しない。メインセッション自身の確認（テストの再実行、差分を読む）が済んでいれば先に進む |

## 実装者

| 症状 | 原因と対処 |
|---|---|
| 実装が設計書から大きく外れる | 設計書の「変更するファイルと関数」「テスト方針」が足りていないことが多い。設計書を具体的にし、同じ実装者に差し戻す |
| 実装者が何度も止まって判断を仰ぐ | 設計書の未決事項が多い。まとめて決めて設計書に反映してから再開する。同じ種類の質問が続くなら、設計の粒度が粗い |
| 報告では「テスト通過」だが、自分で実行すると落ちる | 実装者が別の場所（worktree）で実行している、または一部のテストしか実行していない。並列に動かしたときは、ほかの組のファイルが揃う前の結果のこともある。報告の「作業した場所」と実行コマンドを確かめ、全員が終わってから自分で実行する |
| 並列の実装者が、同じファイルを書いた | 担当の分け方が曖昧だった、または途中から分けた。`git status` と各報告の「変更したファイル」を突き合わせ、持ち主を1人に決めて、その実装者に設計書と照らして確かめさせる |

## Herdr (hc)

| 症状 | 原因と対処 |
|---|---|
| `hc wait` が `reason: timeout` で戻る | まだ実行中。同じコマンドでもう一度待つ。失敗ではない |
| `hc wait` が途中で打ち切られる | Bash ツールの `timeout` が既定の2分のままになっている。`600000` にして `hc wait --timeout 540` で呼ぶ |
| `hc run` が名前の重複で失敗する | 同じ名前の端末がまだ生きている。`hc ls` で確かめ、別の名前（`-2` を付けるなど）で起動する。自分が起動したものでなければ触らない |
| 子エージェントに最初の指示が届かない | 起動結果の `first_message.sent` が `false`。`hc read <名前>` で画面を読み、確認ダイアログに対処してから送る |
| 子エージェントが `blocked` になる | 権限の確認など、人の判断を待っている。ユーザーに画面を見てもらう。`--force` で送って回避しない |
| `$HC_TERMINAL_ID` はあるが `hc` が動かない | Herdr なしの手順（Bash のバックグラウンド実行）に切り替え、切り替えたことを伝える |
