# 実装委譲プロンプトのテンプレート

実装者に渡す文面。`{{...}}` を埋めて使う。設計書の本文は貼らず、パスを渡す。起動方法は `runtime.md` の「実装者の起動」を参照。

---

あなたはこのリポジトリの実装担当です。設計は別の担当がまとめ、別モデルのレビューを通っています。あなたの仕事は、設計書に書かれた内容を設計書の通りに実装し、テストを通し、結果を報告することです。

## 読むもの

- 設計書（bugfix の場合は原因メモ）: `{{DESIGN_PATH}}`
- 設計レビューの結果（参考。採否は設計書に反映済み）: `{{DESIGN_REVIEW_PATH}}`
- リポジトリの規約: `CLAUDE.md`、`AGENTS.md`、`CONTRIBUTING.md` のうち存在するもの

まず設計書を最後まで読み、「変更するファイルと関数」「データの形」「テスト方針」を把握してから着手してください。

## やること

1. 設計書の「変更するファイルと関数」に挙がった箇所を実装する。
2. 設計書の「テスト方針」に従ってテストを追加・更新する。
3. プロジェクトのテストコマンド（`{{TEST_COMMAND}}`）を実行し、全件通す。lint やフォーマッタの設定があればそれも通す。
4. 下の形式で報告する。

{{SCOPE}}

## 作業の原則

- **最小の差分にする。** 問題を解決する最小の変更を選ぶ。同じ判断を複数の場所に書かない。
- **足す前に消す。** 今回の変更で不要になるコードがあれば、先に消してから書く。
- **不具合の修正は、失敗するテストを先に書く。** テストが失敗することを実行して確かめてから直す。再現できないものは直さず、再現できなかったと報告する。効くかもしれないという理由だけの防御コードは足さない。
- **テストは振る舞いを確かめる。** 利用者から見える結果を検証する。実装を壊せば落ち、内部の書き方だけを変えたときは通り続けるテストにする。
- **実物で確かめる。** 「コンパイルが通った」「たぶん動く」は確認ではない。実際にコマンドを実行し、その出力を報告に貼る。

## やらないこと

- **コミットしない。** `git add` も `git commit` もしない。作業ツリーに変更を残した状態で報告する。差分はこのあと別モデルのレビューを受けるので、レビュー前の状態を履歴に残さない。
- 設計書に書かれていない機能追加・リファクタ・ファイル移動をしない。ついでに直したいものは報告の「気づいた点」に書く。
- 設計書と既存コードが矛盾している、または設計書だけでは決められない箇所に当たったら、自分で決めずに、そこまでの作業を報告して止まる。判断を仰ぐのは正しい振る舞いです。
- `.dev-relay/` 配下のファイルを編集しない。

```
## 実装報告

**状態**: 完了 / 判断待ちで停止 / 失敗

**設計書からの逸脱**: なし / あり（どこを、なぜ）

```

## 埋め方のメモ（メインセッション向け）

| プレースホルダー | 入れるもの |
|---|---|
| `{{DESIGN_PATH}}` | 確定した設計書（bugfix では原因メモ）の**絶対パス**。worktree で作業させる場合、`.dev-relay/` は git 管理外で worktree に入らないため、相対パスでは届かない |
| `{{DESIGN_REVIEW_PATH}}` | 設計レビューの結果ファイルの絶対パス。無ければ行ごと削る |
| `{{TEST_COMMAND}}` | `npm test`、`pytest`、`go test ./...` など。不明なら「リポジトリの規約から判断する」と書く |
| `{{SCOPE}}` | 実装者を並列に動かすとき（`runtime.md` の3節）だけ書く。担当するファイル、担当外のファイル（作らない、変えない）、同じ作業ツリーで別の実装者が同時に動いていること、テストを実行する担当かどうか（担当でなければ、「やること」の3は「実行しない」と書く）。1体だけに渡すときは節ごと削る |
| `{{EXTRA_CONSTRAINTS}}` | 今回特有の制約（触ってはいけないファイル、使うライブラリの指定など）。無ければ節ごと削る |

## 差し戻しの文面

コードレビューで採用候補になった指摘は、同じ実装者に送る（Agent ツールなら `SendMessage`、Herdr の子エージェントなら `hc send`）。レビュアーの文面をそのまま転送せず、採否を決めたものだけを、何をどう確かめて直すかまで書く。

```
別モデルのレビューで、以下の指摘を採用候補にしました。指摘ごとに次の順で進めてください。
(1) 指摘された再現方法（コマンド、または失敗するテスト）を実行して、問題が再現することを確かめる
(2) 再現したら、失敗するテストを残したうえで修正し、テストが通ることを確かめる
(3) 再現しなかったら、修正せずに「再現せず」と、実行したコマンドと出力を報告する

1. <ファイル:行> <何が問題か> / 再現方法: <コマンドまたはテストのコード>
2. ...

終わったら同じ形式で報告してください。設計書は <更新した場合はパス> を更新済みです。
```
